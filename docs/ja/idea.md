# 始まりの話（2026-11-24, crux と Claude）

設計は [design-memo.md](design-memo.md) にあります。ここは、どういう話から始まったかの記録です。

1. xipe_totec の更新案として「行 ID の手打ちやコピペが手間なので、隔離手法の実装・sandbox 化（クローンの生成？）」が出た。
2. 問題意識の中身：アプリケーションを作っていて走らせるとき、外部へアクセスするものだと**無駄なアクセスを実行してしまう＝セキュリティ
   リスクを孕む**ことがあった。
3. なので sandbox（ファイル・ネットワーク・外部の状態の全部）ではなく、ネットワークだけにフォーカスした新しいリポジトリにする。
   理屈は DNS や VPN に近いが、アプリケーション（ターミナル？）からのネットワーク接続をインターセプトして、設定しておいたものを返す。
   Xipe Totec の「sandbox はない」という約束は変えない（Xipe はあれば Citlalpol の下で REPL を起動するだけ）。
4. 名前：Citlālpōl は特殊文字が入るので Citlalpol。
5. HTTPS は（もっと広く取って）ローカルホストに曲げてしまう。原理的に固くなる。
   → network namespace と組み合わせれば曲げ先以外の経路がなくなる。TLS の検証は曲げても残るので、偽の応答を返すには CA か
   アプリ側の設定が要る。応答の中身は Citlalpol が作らず、人が用意したローカルの代役が作る。
6. アクセス記録のデーモンを別に立てる。`citl` で、時間ごとのアクセスや全記録を参照できる。
7. アプリケーションを作るときに、アクセスする IP や対向先は明記されるはず。それを `access.json` にまとめてもらい、`citl read` で
   読んで自動で曲げる。
8. 記録をもとに access.json を作る使い方：Xipe Totec で対象のリポジトリを外部遮断のまま走らせ、接続（シェイクハンズ）ができずに
   止まったところや、外へ出ようとして失敗したものを記録する。その記録をもとに access.json を更新し、「アクセスしたらどうするか」を
   決めて、また Xipe Totec で走らせる。段階を「安全な通信か（接続）」「何を送るか」「何を送ったら何が返ってきてほしいか」に分けて
   進めれば、access.json は不必要なシャットアウトをせずに済み、仮想のアクセス先の要件定義もしやすい。
9. サーバーの機能を一部借りればよい（例：TLS の復号）。Citlalpol がローカルのプログラムを起動できるように作れば、Pact より柔軟で
   結合を薄くできる。段階 3 の表を本物に当てて照合するモード（verify）も要るが、照合のプログラムを Citlalpol の中か読めるところに
   置くか、そのパスを伝えておき、ローカルのプログラムの起動として握ればよい。
10. 全体のイメージ：段階的に access.json と防御壁がゆるくなりつつ、verify の代わりのプログラムが実際の計算を補ったり、ローカルの
   計算（何を返せばいいか＝Pact に相当する機能）を Citlalpol で発火させる。
   → design-memo v0.2 の「Xipe Totec で回す」「三つの段階」「ローカルのプログラムを起動する」「verify」の節。Claude から足した点：
   試みを行に結ぶ名札、ゆるめるのは人の承認だけ、記録の秘密を伏せる、unix socket の抜け道、起動の設定は commit されるファイルに書かない。
11. 渡し方（stdin/stdout か fd か）は、アプリ側ではなく起動されるプログラムの側次第。端末越しならどれも可能か？ → 既定は stdio
   （端末越しに人が答える代役もできる）、`fd`（socket activation）と `addr` も選べる形に。
12. 三つの段階のうち 2・3 は、むしろ LSP などの領域。受け取ったものに対してプログラムが発火するので、「何を受け取ったときに何が
   発火したか」はコードを読めるものが対応しなければならない範囲。だから access.json の項目として用意して、設計者が書き込めるように
   する。
13. verify のプログラムは、xipe_totec と embody のように分離する。名前は swallow（vent、embody など、ややマイナーな英単語を意図的に
   選んでいる系譜）。
   → design-memo v0.3。
14. swallow のリポジトリを作った（https://github.com/Crux-xurC/swallow）。設計者が何を返すか・何を発火させるか決めていない場合は、
   デフォルトで swallow とする。→ design-memo v0.3.1、swallow の docs/ja/design-memo.md。
15. Citlalpol の立ち位置（テストの実行時の権限）として、テストより上に来ていないといけない。最初のパターンとして ping を送る
   プログラムを用意し、Citlalpol の外で送れる／Citlalpol の下で起動したときに timeout する／access.json がその IP を持ったときにも
   送れない／返すものを用意できたときに送れる、の 4 段で確かめる。→ Claude の調整：TCP（HTTP）の上の ping、IP でなく名前、
   b は timeout でなく「失敗し記録に残る」（ICMP と IP の版は M6）。
16. 「偽の外」こそが Citlalpol の本体という方が適切かもしれない（通信記録のデーモンもある）。forbidden という「外部へ向かうものを
   強制的に Citlalpol へ」を考える：`forbidden on` でその端末の次のコマンドからは外へ行くにはローカルホストの Citlalpol を経由し、
   `forbidden off` で切れる、というシンプルなシェルを定義する。
   → design-memo v0.4。
17. 権限の位置も考えなくて良くならないか：Citlalpol を例えば 4600 に充てて、4600 から通信すると考えればいい。
   → Claude：要るのは「壁を作る側が親で、対象から見える外は扉だけ」の一つ。PID namespace などは記録の正しさのためで今の範囲では
   過剰。4600 はホスト側でなく壁の中にだけ開く（外の誰もが使える口にしない）。
18. forbidden を別のリポジトリにした（https://github.com/Crux-xurC/forbidden）。順序：forbidden で通信を止められるか・off にできるか
   → Citlalpol を小規模に localhost として経由して ping を送れるか → ping の 4 段。文書としては「Citlalpol を使って契約テストをする際は、
   forbidden を入れた上で実行して、契約テストが不用意に外に行かないことを確かめてください」。Citlalpol は access.json に記載のない
   ものを全面禁止で作ればよくなるから簡単になる。
   → design-memo v0.5（壁と namespace・shim・抜け道・権限の位置は forbidden へ。Citlalpol は扉の向こうで SOCKS5 と HTTP proxy を
   受けるだけ。宛先は接続の最初に名乗られるので DNS の細工が要らない。名札は壁の外から付ける）。
19. forbidden の扉の一覧の決まり（壁の外からだけ変える、unix socket が既定）と、localhost（Citlalpol）への通信に HAProxy の PROXY
   protocol を乗せること（Citlalpol から全部が 127.0.0.1 から来たように見える問題を解く）。
20. 応用：他者の作ったものを調べるときに Citlalpol を使う（安全性の分からないプログラムを、Citlalpol というローカルホストに限定して、
   不透明なホストへのアクセスを禁じる）。forbidden に `--strict` を入れる。
   → design-memo v0.6（PROXY v2 は扉の socket からだけ、記録に pid とコマンド、宣言のない名前は引く前に禁止、調べるときは pass を置かない）。
